# tbc-contract JS 1.6.5 Parity Design

## Objective

Bring `tbc-contract-go` into protocol and public-feature parity with
`TuringBitChain/tbc-contract` version `1.6.5` at commit
`19acaa0e279c39741c9957e1236b3eac9ff4154a`, then verify the implementation
with deterministic automated tests and minimal-value transactions on TBC
testnet.

The JavaScript repository is the byte-level reference for locking scripts,
unlocking scripts, transaction layout, sighash-related preimages, fees, and
change placement. Go APIs may use idiomatic names and error returns, but their
observable transaction behavior must match JavaScript.

## Scope

### Phase 1: Protocol compatibility foundation

- Add FT version detection that distinguishes FT v1, v2, v3, and StableCoin
  scripts. FT v2 and v3 have the same byte length, so version detection must
  inspect the fill-character opcode used by JavaScript rather than relying only
  on script length.
- Extend signed and externally signed FT contract unlock builders for the FT v3
  input-index marker and `isContractTXs` behavior.
- Apply FT v3 handling to Pool NFT 2.0, MultiSig FT transfers, OrderBook, HTLC,
  and every other composed transaction that spends FT contract outputs.
- Synchronize embedded FT mint, Pool NFT/FTLP, and StableCoin scripts with the
  JavaScript 1.6.5 source, including the June 2026 padding and legacy FTLP
  compatibility fixes.
- Preserve support for FT v1/v2 and existing StableCoin outputs.

### Phase 2: Token HTLC

- Port the JavaScript FT/StableCoin HTLC lifecycle:
  `DeployHTLCToken`, `FillSigDeployHTLCToken`, `WithdrawHTLCToken`,
  `FillSigWithdrawHTLCToken`, `RefundHTLCToken`,
  `FillSigRefundHTLCToken`, and the three direct-signing variants.
- Preserve the JavaScript input order, output order, maximum five FT inputs,
  ancestry data requirements, sequence/lock-time rules, and signature order.
- Support FT v2, FT v3, and StableCoin inputs wherever JavaScript 1.6.5 does.

### Phase 3: Token OrderBook

- Add FT-to-FT and StableCoin-compatible token sell and buy order scripts and
  order-data parsing.
- Port offline transaction building and signature filling for create, cancel,
  and match operations.
- Port direct/online wrappers after the offline primitives are verified.
- Preserve partial-fill behavior, token-pair validation, fee outputs, remaining
  order placement, and fixed script lengths from JavaScript 1.6.5.

### Phase 4: Smaller parity gaps

- Add FT transfer with additional OP_RETURN information.
- Add the Pool NFT 2.0 local-input FT-to-TBC swap entry point.
- Add missing online wrappers where they provide behavior beyond the existing
  Go signed builders.
- Correct documentation that still describes the current StableCoin
  implementation as build-tagged or frozen.
- Keep Pool NFT v1 out of this migration. It remains an explicitly unsupported
  legacy family unless separately requested.
- Do not port deprecated JavaScript-only convenience methods when an existing
  Go method already provides the same behavior.

## Architecture

### FT version boundary

Introduce one shared FT script classifier in `lib/util`. It accepts locking
script bytes or hex and returns a typed version and StableCoin flag. Contract
packages must not duplicate length-only detection. The classifier becomes the
single source for Pool, MultiSig, OrderBook, and Token HTLC.

FT v3 unlock construction extends the current FT swap unlock path with the
input-index opcode required by JavaScript. Existing v1/v2 output must remain
unchanged for the same fixtures.

### Script templates

Large scripts remain embedded resources under `lib/contract/asm`. Templates are
copied from the JavaScript 1.6.5 source and parameterized only at the same
substitution points already used by Go. Tests compare rendered script hex and
script length against JavaScript-generated golden fixtures.

### Token HTLC

Token HTLC lives in a focused Go source file next to the existing TBC HTLC
implementation. Shared HTLC validation and code-script helpers may remain in
`htlc.go`; token-specific transaction assembly and signature filling remain
isolated to avoid making the TBC-only path harder to audit.

### Token OrderBook

Token-order code is separated from the existing TBC/FT OrderBook transaction
assembly where practical, while sharing common order validation and signature
helpers. Public names follow the existing Go naming style and map directly to
the JavaScript methods.

### API and network separation

Transaction construction remains deterministic and testable without network
access. API fetching and broadcasting stay in `lib/api` or test harnesses.
Online convenience methods compose the offline primitives rather than
duplicating transaction logic.

## Automated Testing

All new production behavior follows red-green-refactor:

1. Add a test that fails because the behavior or method is absent or incorrect.
2. Run the focused test and confirm the expected failure.
3. Implement the minimum behavior required.
4. Run the focused test and the full suite.

Tests are added as real `*_test.go` files, not executable examples with boolean
switches. Coverage includes:

- FT v1/v2/v3/StableCoin classification fixtures.
- FT v3 unlock-script input-index markers and v1/v2 regression fixtures.
- Rendered FT, FTLP, Pool, and StableCoin script length and hex hashes.
- Token HTLC deploy/withdraw/refund transaction structure, signature filling,
  invalid ancestry, invalid secret, input limits, and lock-time handling.
- Token Order create/cancel/full-match/partial-match structure, order-data
  round trips, pair mismatch, insufficient balance, and fee handling.
- Additional-info FT transfer and local Pool swap transaction layout.
- JavaScript-generated golden fixtures stored without private keys.

The repository-wide verification commands are:

```bash
go test ./...
go test -race ./...
go vet ./...
```

## Testnet Broadcast Validation

Only TBC testnet endpoints are permitted. No mainnet endpoint or mainnet
broadcast is allowed.

The supplied WIF is used only at runtime to sign testnet transactions. It must
not be added to new source, fixture, environment file, command argument, or
test output. Existing tracked test drivers that contain WIF literals are
converted to environment-variable inputs before broadcast work begins.

The broadcast harness will:

1. Derive the funding address locally and query its testnet balance/UTXOs.
2. Generate ephemeral participant keys for sender/receiver and
   buyer/seller/matcher roles.
3. Fund those addresses with the minimum practical testnet TBC.
4. Mint isolated test FT contracts needed by the scenarios.
5. Broadcast and verify:
   - FT mint and self-transfer using the current FT version.
   - Token HTLC deploy and withdraw.
   - A second Token HTLC deploy and refund when the chosen lock time permits.
   - Token sell/buy order creation, cancellation, and a matched FT-to-FT order.
   - Pool NFT 2.0 creation and a minimal lifecycle operation needed to exercise
     the synchronized FTLP script.
6. Broadcast chained transactions strictly in parent-before-child order.
7. After every broadcast, record the txid and verify it through the testnet API
   or mempool/transaction endpoint before proceeding.
8. Return spendable residual TBC from ephemeral addresses to the funding
   address where transaction structure permits.

StableCoin admin broadcasts are excluded because they require an external
MuSig2 ceremony and an authorized aggregate admin key. StableCoin script parity
is verified with deterministic golden tests instead.

If the testnet funding balance, index API, or broadcast service is unavailable,
the automated suite still runs to completion and the exact external blocker is
reported. Failed network calls are not treated as implementation success.

## Error Handling and Safety

- Amounts remain integers: TBC in satoshis and FT in raw minimum units.
- No float is used in production transaction arithmetic.
- Builders validate script version, ancestry-array lengths, maximum FT inputs,
  output amounts, and fee sufficiency before signing.
- Network retries are restricted to read-only requests. Broadcast POSTs are
  not blindly retried.
- Testnet transaction logs redact WIFs, raw private keys, and ephemeral secret
  material.
- Existing APIs remain source compatible where possible. Any unavoidable
  signature change receives a compatibility wrapper or a migration note.

## Deliverables and Success Criteria

- Go supports FT v3 throughout all composed contract paths without regressing
  FT v1/v2 or StableCoin handling.
- Embedded scripts match JavaScript 1.6.5 golden fixtures.
- Token HTLC and Token Order public Go APIs cover the JavaScript 1.6.5
  lifecycle.
- Smaller in-scope parity gaps are implemented and documented.
- The repository contains deterministic unit and parity tests.
- `go test ./...`, `go test -race ./...`, and `go vet ./...` pass.
- Testnet broadcasts produce verified txids for every feasible scenario listed
  above, with any external or protocol limitation explicitly documented.
