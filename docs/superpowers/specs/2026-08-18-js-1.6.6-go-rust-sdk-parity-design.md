# JS 1.6.6 Go and Rust SDK Parity Design

Date: 2026-08-18

## Goal

Synchronize the Go contract SDK and the contracts already managed by the Rust
SDK with the released npm package `tbc-contract@1.6.6`. Add the newly released
TBC20 protocol and TokenValidator to both SDKs. Preserve the ability to spend
assets created by older SDK versions and prove the result with deterministic
JavaScript parity fixtures, local script execution, and real TBC testnet
broadcasts.

The JavaScript npm release is the protocol authority. Current development
branches, documentation prose, and either port are secondary references.

## Repository scope

### Go SDK

The Go SDK follows every relevant JavaScript 1.6.6 change in contract families
it already exposes and adds the two new 1.6.6 capabilities:

- FT v4 creation, recognition, spending, and compatibility with FT v1-v3.
- NFT v2 default creation and spending, while retaining explicit support for
  the NFT versions the Go SDK already supports.
- StableCoin v4 creation and spending, including existing older StableCoin
  scripts.
- Pool NFT v2 plan 6, canonical plan/fee/address rules, FT v4 support, and the
  1.6.6 Pool correctness and security fixes.
- OrderBook input limits and FT v4 support.
- MultiSig and token HTLC support for FT v4 through the shared FT machinery.
- The new TBC20 protocol as a separate contract family from legacy FT.
- The new TokenValidator with the same classification and validation outcomes
  as JavaScript.
- Regression coverage for unchanged Go-managed contracts, including native
  HTLC and PiggyBank.

Pool NFT v1 is intentionally excluded. No compatibility implementation or new
test coverage will be added for it.

### Rust SDK

The Rust SDK synchronizes only contract families it already manages, plus the
two newly approved 1.6.6 capabilities:

- FT v4, including old FT recognition and spending.
- NFT v2, including old NFT recognition and spending.
- StableCoin v4, including old StableCoin recognition and spending.
- Pool NFT v2 plan 6, canonical fee rules, FT v4 support, and the relevant
  1.6.6 Pool fixes.
- OrderBook input limits and FT v4 support.
- MultiSig FT v4 support through the shared FT machinery.
- New TBC20 support.
- New TokenValidator support.

Rust will not add HTLC, PiggyBank, or Pool NFT v1. This project is not intended
to fill historical Rust feature gaps unrelated to the 1.6.6 synchronization.

### Wallet

`turing-wallet` is out of scope for this implementation. After the Rust SDK is
released, a separate wallet project will add NFT v2, FT/StableCoin v4, Pool
plan 6, new TBC20 asset operations, TokenValidator-backed approval checks, and
the associated signing and preview changes. The wallet's existing `tbc20`
label for legacy FT must not be treated as the new TBC20 protocol identifier.

Publishing either SDK and modifying the wallet are not authorized by this
design.

## Compatibility model

New creation methods use JavaScript 1.6.6 defaults:

- NFT creates v2 scripts by default.
- FT creates v4 scripts by default.
- StableCoin creates the v4 FT-derived script family by default.
- TBC20 is exposed as its own family and never aliases the legacy FT family.

Version detection is additive. Existing public methods must continue to spend
previously supported NFT, FT, and StableCoin outputs. A caller can explicitly
request a retained older creation path where the JavaScript release provides
one. Unknown or malformed versions fail with a typed/descriptive error; they
must not silently fall back to another script family.

The Go and Rust public interfaces remain idiomatic for their languages. Exact
method names do not need to imitate TypeScript when that would break the
existing SDK style, but transaction behavior, limits, script bytes, sighashes,
and validation outcomes must match JavaScript.

## JavaScript oracle and deterministic fixtures

A fixture generator will install exactly `tbc-contract@1.6.6` in an isolated
directory and record its package version and integrity metadata. It will
generate deterministic cases for every changed script family and transaction
shape.

Fixtures will cover at least:

- NFT old and v2 code scripts, version detection, collection, mint, batch
  mint, transfer, and transfer with TBC.
- FT v1-v4 recognition, v4 mint code, tape, transfer, additional-info
  transfer, batch transfer, and merge.
- StableCoin old and v4 mint code, create, administrator mint, transfer,
  batch, merge, freeze, and unfreeze structures.
- Pool plans 1-6, exact plan-to-fee and plan-to-service-address mappings,
  standard and locked scripts, LP scripts, and every 1.6.6 state-transition
  fix.
- OrderBook boundary cases for sell, buy, and total input caps, plus FT v4.
- MultiSig FT v4 deposits and spends.
- Token HTLC FT v4 cases in Go only.
- TBC20 script/tape layouts, amount encoding and range checks, input/output
  limits, the exported `mint`, `transfer`, and `merge` operations, transfer
  token/change output groups, and merge slot compaction.
- TokenValidator VALID, INVALID, and UNKNOWN outcomes for legacy FT, TBC20,
  and malformed or incomplete transactions under strict and relaxed-metadata
  policies.

Signatures are not expected to be byte-identical across languages. Parity is
measured before nondeterministic signing and at deterministic boundaries:
locking scripts, tapes, transaction layout, outpoints, amounts, sequences,
locktimes, sighash preimages/digests, and validation results. Fully signed
transactions must execute successfully against the same parent scripts and
produce the same economic state transition.

Fixture generation is test support, not a runtime dependency. Neither SDK may
invoke Node.js or ship JavaScript as part of normal operation.

## Implementation boundaries

Each contract family owns its script constants, parsers, builders, and tests.
Shared version recognition lives in the existing common FT/NFT paths so that
StableCoin, Pool, MultiSig, OrderBook, and Go token HTLC cannot drift into
separate version tables.

TBC20 is implemented in a new module in each SDK. It has its own types,
builders, limits, script recognition, and transaction ancestry handling. It
must not reuse a legacy FT enum or a string named `tbc20` whose semantics are
legacy FT.

TokenValidator is a read-only validation layer. It classifies supported token
families, checks their structural and value invariants, and returns the same
three-state result as JavaScript. UNKNOWN is distinct from INVALID: callers
may surface or defer an unknown contract, while an invalid transaction must
not be presented as valid.

Input-count, amount, plan, tape-size, and version constraints are checked
before signing. Errors include the violated field and accepted boundary so the
same failures can be asserted in Go, Rust, and JavaScript fixtures.

## Test-driven implementation

Work proceeds one behavior at a time:

1. Generate or select a JavaScript 1.6.6 fixture.
2. Add a focused Go or Rust test that fails for the missing behavior.
3. Confirm the failure is caused by the intended parity gap.
4. Add the smallest implementation needed for that behavior.
5. Run the focused test and the relevant contract-family suite.
6. Refactor only after the tests pass.
7. Run the complete repository suite before moving to live validation.

Negative boundary tests are required for all new limits. Backward
compatibility tests must use preserved old scripts rather than recreating them
through a new default builder.

## Testnet broadcast verification

Live testing uses only `https://api.tbcdev.org/api/tbc/` and the user-approved
testnet key. The key is provided to a process through standard input and held
only in a runtime environment variable. It is never placed in source code,
fixtures, command arguments, shell history, logs, reports, or commits.
Ephemeral participant keys for MultiSig and OrderBook are generated at runtime
and are likewise not recorded.

Go and Rust receive independent live lifecycles and independent spendable
UTXOs. An accepted transaction built by one SDK is not evidence that the other
SDK can construct and sign the operation.

Before any POST, every transaction is parsed, checked for expected structure
and value flow, checked for signed-size fees, and executed against its contract
parent scripts where the repository interpreter supports it. Broadcast POSTs
are single-attempt and are never automatically retried. Read-only API calls
may retry transient failures.

Each accepted transaction is fetched back from the public testnet API and
verified for:

- returned txid and serialized raw bytes;
- referenced parent outputs and expected contract family/version;
- output amounts and intended owner or contract state;
- paid fee and signed-size target fee;
- the next lifecycle step's use of the accepted state.

The live matrix covers every economically distinct changed path and a
regression path for each managed contract family. It includes, as applicable
to each SDK:

- NFT collection, single/batch mint, v2 transfer, and transfer with TBC.
- FT v4 source/mint, transfer, additional-info transfer, batch, and merge.
- StableCoin v4 create, administrator mint, transfer, batch, merge, freeze,
  and unfreeze.
- Pool NFT v2 plan-6 creation, initialization, increase, both swap directions,
  consume, LP merge/burn, pool-held FT merge, and locked variants affected by
  1.6.6.
- OrderBook create/cancel/full match/partial match using FT v4; rejected input
  limit cases remain offline because invalid transactions must not be posted.
- MultiSig TBC regression plus FT v4 deposit and both spend destinations.
- Go-only token HTLC v4 withdraw and refund lifecycles.
- TBC20 source/genesis mint, transfer with token and change output groups, and
  merge, followed by on-chain validator checks of accepted transactions.

Validator INVALID fixtures and other deliberately invalid limit cases are
never broadcast.

Evidence is committed as public txids, byte sizes, fee calculations, expected
state transitions, and reproducible read-only verification commands. Private
keys, preimages, signatures, and unbroadcast raw transactions are excluded.

## Delivery sequence

1. Freeze the JavaScript 1.6.6 oracle and produce the complete gap/fixture
   matrix.
2. Implement shared version recognition and NFT/FT/StableCoin parity in Go.
3. Implement Pool, OrderBook, MultiSig/token-HTLC updates in Go.
4. Add Go TBC20 and TokenValidator.
5. Complete Go static, race, fixture, interpreter, and testnet verification.
6. Implement the corresponding managed-contract changes in Rust.
7. Add Rust TBC20 and TokenValidator.
8. Complete Rust format, lint, fixture, interpreter, and independent testnet
   verification.
9. Run cross-SDK fixture comparison, secret scanning, and evidence review.

Work in the Rust repository must preserve the existing untracked
`examples/repro_ft_full_self_transfer.rs` file unless the user separately asks
to incorporate or remove it.

## Completion criteria

The synchronization is complete only when:

- every in-scope JavaScript 1.6.6 fixture matches in both applicable SDKs;
- old supported NFT/FT/StableCoin fixtures still pass;
- complete Go and Rust test, build, format, lint/static-analysis, and patch
  hygiene checks pass;
- every required live lifecycle transaction is accepted and refetched on TBC
  testnet;
- live evidence contains no secret or unbroadcast transaction material;
- the final gap matrix contains no unexplained in-scope difference.
